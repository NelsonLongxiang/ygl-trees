# ygl-trees 路线图

> 定稿依据：评审席提案（2026-10-27）→ 总工席意见（direct-b713604d；PR 复审 direct-612fb22c 增补 G9/G10）→ 属主裁定：「同意总工席版本：评审席从 fork 起草 docs/roadmap.md 的 PR（含总工席增补的门禁与「暂不做」项），属主裁定队列另开 GitHub 讨论 issue。」
>
> 分工：本文只写**主题、顺序、依赖、出口条件**。做了什么、何时做的记在 [plan.md](plan.md)（执行记录）与 CHANGELOG；需要属主拍板的事项统一进裁定队列 [#94](https://github.com/NelsonLongxiang/ygl-trees/issues/94)。各项进度以对应 issue 的完成清单为准，本文不写状态注记（[doc-governance.md](doc-governance.md)「一事实一家」）。

## 一、为什么要收窄

1. **主线太多。** 同时在推的有：PG 写后端（B0–B7）、验证器 SDK 与验证器包（SDK-0..5、VP-0..4）、品味提取（#27）、研究工作台本体（#80、#82），以及 Rust 双实现、Bun 运行时。
2. **节奏快于质量。** 0.115.0 → 0.116.0 约两天，期间 #86–#93 共 8 个回归或缺陷，多数是推送之后才由评审发现，例如离线测试依赖线上服务（#90）、提交说明声称改了实际没提交、门禁假绿（#93：PG 腿对着不可达的 PG 也判通过）。
3. **关键路径没有排期。** `verify tree run`（SDK-2）挡着 VP-3 及之后的组合能力；verify-on-PG 挡着 PG 腿的真实验收（`pg-write-backend-plan.md` 护栏 ① 的原始目标）。

## 二、三段主题

### 现在（约 1–2 周）：稳定与门禁加固

**纪律**
- **按批发版**，不再一处修复发一版。适用于整个舰队，包括 market 线，不只 ygl-trees。

**门禁（每条都要能机器检查）**

| # | 门禁 | 判据 |
|---|---|---|
| G1 | 离线门 | 干净克隆、无任何凭证（无 `AI_GATEWAY_API_KEY` / `YGL_DB_URL` 等）跑 `pnpm test` rc=0 |
| G2 | 全量 diff 门 | 任何快审 / 双审盖章前必须读完整 diff；按 grep 过滤过的行不算读过（PR#140 事故） |
| G2b | 未结复核阻断合并 | PR 上有未结的评审「要求修改」（REQUEST-fix）时，禁止合并——PR 合并、直推、直接合并提交一律不行；只有评审方书面解除才放行（总工席 direct-69c94231，2026-10-27。起因：本地合并提交 8e210ac 生成于 15:14:23Z，早于评审「要求修改」15:16Z；违规点是 15:30:34Z 推送合并——阻断已开 14 分钟，缺陷转 #101） |
| G3 | 真调用门 | 工具 / MCP 类判据必须有一次真实往返；`tools/list` 里出现不算证明 |
| G4 | 提交说明对账 | 提交说明声称的改动逐条对照 `git show --stat` 与 diff；声称了却不在 diff 里 = 红 |
| G5 | 关键测试变异校验 | 钉住关键行为的测试，要能证明删掉 / 改坏被钉的那一行时测试变红 |
| G6 | 棘轮重锁归因 | `ratchet-baseline.json` 任何上调必须写明当日裁定编号和增量归因（例：#83 的 +6.2 KB 与 ~14.6 KB 漂移分开记） |
| G7 | 真 PG 矩阵 | `scripts/dual-backend-matrix.mjs --strict` 对真实 docker `postgres:16` 跑，镜像版本在 CI 钉死；对不可达 PG 必须 rc≠0 |
| G8 | 发布后复跑基线 | 每次发布后，从 npm 包 + `v*` 标签干净克隆复跑关键测试（含 bootstrap / 安装路径），结果记进对应 issue |
| G9 | 合并祖先守卫 | 推送前检查远端基线分支（ygl-trees 为 `origin/master`，其他仓按各自默认分支）是本地基线分支的祖先，否则拒推；每次合并后记录并复核 `git merge-base --is-ancestor <合并 sha> <远端基线分支>` rc=0——防「回执是真的、代码却不在主干上」（dad595b 丢失为第二例） |
| G10 | 代理面冒烟 | 有代理面的仓（如 market 的 `/go/<id>/`），E2E 必须恒含三探针：`/go/<id>/` 页面加载、静态资源 200、`/api` 透传探针——常规 E2E 漏过了四层白屏缺陷。**market 线专用**：ygl-trees 无代理面不适用（#96 条目 9；跟踪在市场线 direct-7bb925af） |
| G11 | 仓内体量门 | `docs/spec.md` 总字节与 `docs/` 活跃字节（不含归档）双上限（`volume-baseline.json`）；超限必须先按 plan.md 拆分模式归档，否则红；测量失败或量出 0 一律 rc≠0（`scripts/volume-gate.mjs`；总工席 A 项增补，属主授权，见 #94 零·二） |
| G12 | 解释器锚 | `scripts/*.sh` 的 shebang 与实际执行解释器一致，pnpm scripts 里的 shell 链经 `scripts/run-sh.mjs` 钉死解释器；漂移即红（`scripts/interp-anchor.mjs`；总工席 D 项增补，属主授权，见 #94 零·二） |
| G13 | 可复制命令引号门 | 产品代码生成的任何可复制命令串，每个自由文本插值都必须作为一个 POSIX 单引号词输出（内嵌 `'` 转义为 `'\''`）；判据：四类恶意名（`x;touch /tmp/pwn` 型、`a$(id)` 型、含空格、含引号）的逐字文本测试，并全量扫过 resolveCommand 一族。与 G12 成对：入口钉解释器、出口给参数加引号（总工席 direct-6334be35，属主授权，见 #94 零·二；起因 #101） |

**出口条件**
- 连续 3 个版本（N=3，属主 2026-10-27 裁定，见 #94 第零节）没有「发布后才发现」的回归。
- G1–G13（含 G2b）全部有脚本或检查清单落地，并在一次实际发版中全部执行过（G10 只对有代理面的仓适用）。
- `--strict` 矩阵在真 PG 上为绿。

### 下一步（约 2–6 周）：打通两条关键路径

1. **SDK-2 `verify tree run`**
   - 让各验证器仓库不再手写编排；是 VP-3「模式即树模板」的前置（验证器包 D6 裁定）。
   - 出口：评审验证器改用 `tree run` 组合，连续 2 轮根结论、叶子结论与现行编排一致（K=2，属主 2026-10-27 裁定，见 #94 第零节）。
2. **PG B5 / B6 收尾**
   - verify-on-PG、webui 读 PG、D2 库内绑定记录、D4 会话 id 要求。
   - 出口：双后端矩阵在真 PG 上全绿（unit + demo + contract-audit + readme-verify + verify 链），再把 `pg-write-backend-plan.md` 护栏 ① 恢复为原始表述（self-check 双后端）。
3. **研究工作台缺口**
   - #80 verify 谓词能力（视图 / 派生表 / pragma）、#82 `project rm`。
   - 出口：两个 issue 的完成清单在发布包上复核通过。

### 以后：生态与长期探索

| 项 | 开工前置 |
|---|---|
| 验证器包 VP-2..4（安装、信任、跨仓组合） | VP-3 要等 SDK-2；VP-4 要等 SDK-5 `import-report` |
| #27 品味提取闭环 | 品味方案 D1–D6 在 #94 裁定 |

每一项开工前先在 #94 有属主裁定，并按 issue 惯例写好涉及位置、编号完成清单与关单条件。

## 三、暂不做

- 三条主线（PG、验证器、研究核心）收口前，**不开新仓库**；Bun 与 Rust parity 排队，不并行。
- SDK-2 `tree run` 落地前，**不把新判据绑定到 tree run 组合**。
- VP-3 落地前，**不扩新的验证模式**（6 种模式词表保持首版，验证器包 D3）。
- B6 在真 PG 上全绿前，**不对外宣称 PG 写入能力**。

## 四、里程碑写法

沿用 issue 的写法，每个里程碑必须有：
1. 涉及的位置（文件 / 命令面）；
2. 编号的、可机器检查的完成清单；
3. 关单条件：以 npm 发布包 + `v*` 标签干净克隆复核通过为准（G8）。

路线图改版时同步核对 #94 的裁定状态。
