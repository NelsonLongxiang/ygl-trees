# ADR：P1 与发布冻结窗口

## 上下文（Context）

ygl-trees 已有生产消费方（.157 专家团的验证器电池、workbench-market 工具面）。0.115→0.116 两天内出现 #86–#93 共 8 个回归，多数是**推送之后**才由评审发现（离线测试依赖线上服务、提交说明与 diff 不符、门禁假绿）。0.116.1 安全 hotfix 又暴露了「hotfix 范围纪律」的必要性：范围=仅安全修+docs，余不入。

同时，P1（生产一号线）是规划中的常态化快速通道——若 P1 与发布冻结无边界，热修会变成事实上的滚动发布，「按批发版」纪律失效。

## 决策（Decision）

1. **冻结窗口**：从「发布候选提交」（版本号 bump 进 master）到「npm 发布 + tag + reviewer 复跑绿」期间为冻结窗。窗口内 master 只收：(a) 阻断发布的修复 (b) 属主明令安全 hotfix。其余一律排队。
2. **P1 通道**：P1 类生产问题（用户面阻断）走 hotfix 路径，但**必须**满足 hotfix 范围纪律（仅该修+docs），且走独立 PR + 评审席放行（G2b），不得直推 master。
3. **发布节奏**：常规版本按批（roadmap「Now」出口=N=3 连续无发版后回归）；hotfix 不计入 N=3 的分母（它是对既有版本的最小修复，不是新风险面）。
4. **解冻条件**：G8 tag 克隆复跑 + 验证席工件级复验双绿 → 解冻下一轮。

## 后果（Consequences）

- 正面：回归窗口收窄到「发布过程内」而不是「发布后 N 天」；hotfix 范围可审计（PR diff 即范围）。
- 负面：紧急修复的平均延迟增加一个评审周期（G2b）；对「属主 GUI 直纠」的例外仍保留（最终否决权在属主）。
- 度量：发布后回归数（目标 N=3 连续为 0）；hotfix PR 的 diff 行数（范围纪律的代理指标）。
